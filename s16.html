16.1 Sta je CI/CD i uloga QA-a

CI (Continuous Integration) je praksa automatskog build-ovanja i testiranja koda pri svakom commit-u. CD (Continuous Delivery) prosiruje CI automatskim deploy-om na visa okruzenja.

QA uloga: automatizovani testovi su gatekeeper koji sprecava isporuku defektnog koda. Svaki failovani test blokira pipeline.

16.2 Tipicna struktura CI/CD pipeline-a

Code Commit (git push / PR)
       |
  [1] Build       — kompajliranje, dependency restore
  [2] Unit Tests  — brzi, izolovani. Fail -> pipeline staje.
  [3] Static Analysis — linting, code coverage threshold
  [4] Deploy na Test okruzenje
  [5] Integration Tests — API, DB integracija
  [6] E2E / UI Tests   — Selenium, kriticni happy path scenariji
  [7] Deploy na Staging
  [8] Smoke Tests na Staging
  [9] Deploy na Produkciju
  [10] Smoke Tests na Produkciji

16.3 Azure DevOps YAML pipeline — Selenium C# primer

trigger:
  branches:
    include: [ main, develop ]

pool:
  vmImage: windows-latest

steps:
- script: dotnet restore
- script: dotnet build --configuration Release
- script: |
    dotnet test --configuration Release
             --logger trx
             --results-directory $(Agent.TempDirectory)/TestResults
  env:
    BASE_URL:  $(STAGING_URL)
    HEADLESS:  true

- task: PublishTestResults@2
  condition: always()
  inputs:
    testResultsFormat: VSTest
    testResultsFiles: $(Agent.TempDirectory)/TestResults/*.trx

U pipeline-u se izvrsavaju Selenium UI testovi (Sekcija 13), API testovi (Sekcija 15) i unit testovi — sve strukturirano po framework arhitekturi iz Sekcije 19.

16.5 Best practices za testove u CI/CD-u

  • Testovi moraju biti deterministicki — isti ulaz, isti rezultat uvek.
  • Paralelizacija: grupisati testove da se izvrsavaju paralelno.
  • Flaky testovi moraju biti izolovani i oznaceni, ne ignorisani.
  • Koristiti headless mode za browser testove u CI.
  • Cuvati screenshots i logove samo za failovane testove.
  • Retry logika samo za infrastrukturne greske, ne za legitimne failove.

16.6 Tipovi pipeline-a — Scheduled vs. Gated Build

TipTriggerSvrhaKad se koristi
Scheduled (Nightly)Vremenski — svake noci u definisano vremeFull regression suite — svi testovi, sva okruzenjaNightly build za kompletan pregled stanja sistema.
Gated Build (PR validation)Pull Request kreiran ili azuriranBrzi smoke/sanity — blokira merge ako testovi padnuSvaki PR pre merge-a u main/develop granu.
Standard Build (CI)Svaki push na definisanu granuBuild + unit testovi — brzi feedback loopKontinualna integracija tokom dana.
# Azure DevOps — Gated Build (PR validation pipeline)
trigger: none    # ne triggeruje se na push

pr:
  branches:
    include: [ main, develop ]

steps:
- script: dotnet build --configuration Release
- script: dotnet test --filter "Category=Smoke"
          --logger trx
  displayName: "Run Smoke Tests (PR gate)"
Gated Build drzi kvalitet pre merge-a — nijedan PR ne moze proci ako smoke testovi padnu. Nightly suite pokriva sve ostalo. Kombinacija oba je standard u enterprise timovima.

16.7 Git workflow za QA

QA automation inzenjer radi sa Git-om svakodnevno — check-in automation skripti, branching za nove test suite-ove, PR review test koda. Osnovni koncepti:

KonceptQA kontekst
BranchFeature branch za novi test suite ili fix: fix/login-flaky-locator, feature/checkout-regression
CommitAtomski commit — jedan fix ili jedan novi test. Poruka: "Fix: stabilize LOV overlay wait in MaterialPage"
Pull RequestCode review za test kod pre merge-a u main. Reviewer proverava naming, lokatore, wait strategiju.
Merge conflictNastaje kad dva QA inzenjera menjaju isti Page Object. Resava se rucno u Visual Studio.
ChangesetJedinica rada — obicno 2-4 fajla: lokator update + Page Object fix + test scenario azuriranje.
# Tipican QA daily Git workflow
git pull origin develop           # sync sa poslednjim promenama
git checkout -b fix/material-lov  # nova grana za fix

# ... edit Page Object, fix lokator, run locally ...

git add Pages/MaterialPage.cs Tests/MaterialTests.cs
git commit -m "Fix: re-find LOV overlay before click to prevent stale ref"
git push origin fix/material-lov

# Kreirati PR → code review → merge → nightly suite pokuplja promenu

16.8 fetch vs. pull, merge vs. rebase

fetch vs. pullgit fetch preuzima promene sa remote-a ali ne dira trenutnu granu — bezbedno, samo za pregled. git pull = fetch + merge, odmah menja radnu granu.
merge vs. rebaseMerge pravi merge commit i cuva kompletnu istoriju grananja. Rebase "prevlaci" commit-e na vrh druge grane i prepisuje istoriju — linearnija ali opasnija na deljenim granama. Za feature branch pre PR-a rebase je cesto ok; na develop/main koristiti merge.
.gitignoreIskljucuje build output (bin/, obj/), IDE fajlove (.vs/), test rezultate (TestResults/) i kredencijale iz repo-a.
// Resavanje merge konflikta u Page Object-u
// 1. git status -> vidi koji fajl je u konfliktu
// 2. Otvoriti fajl, naci markere:
<<<<<<< HEAD
lokator koji si ti promenio
=======
lokator koji je kolega promenio
>>>>>>> branch-name
// 3. Odluciti koji lokator je tacan (ili spojiti oba), obrisati markere
// 4. git add  -> git commit -> git push

16.9 Test parallelizacija u praksi

xUnit — CollectionsTestovi u istoj [Collection("...")] se izvrsavaju sekvencijalno medju sobom, ali razlicite kolekcije paralelno. Default: xUnit paralelizuje po test klasi.
Thread-safety drajveraSvaki paralelni test MORA imati svoju IWebDriver instancu (npr. kroz [ThreadStatic] ili DI per-test lifetime) — deljeni drajver izmedju paralelnih testova izaziva nasumicne, tesko-reprodukovive failove.
Selenium Grid / DockerParalelni testovi trebaju paralelne browser instance — Grid sa vise node-ova (videti Sekciju 17.6) omogucava da 10 testova stvarno rade istovremeno umesto da cekaju jedan browser.
Test izolacija podatakaPreduslov za bezbednu paralelizaciju — ako dva paralelna testa dele isti test podatak (npr. isti SpecId), nastaje race condition. Svaki test kreira svoje podatke sa unikatnim sufiksom.
// xUnit — onemoguciti paralelizaciju izmedju SPECIFICNIH testova koji dele resurs (npr. isti DB seed)
[Collection("DatabaseCollection")]
public class MaterialTests { ... }

[Collection("DatabaseCollection")]
public class SpecificationTests { ... }
// Obe klase sad idu sekvencijalno jedna za drugom, ali paralelno sa svim ostalim kolekcijama

// xunit.runner.json — globalno podesavanje paralelizma
{
  "parallelizeTestCollections": true,
  "maxParallelThreads": 4
}
Paralelizacija ubrzava regression suite, ali uvodi novu klasu flaky testova (deljeni resurs, race condition) — uvek prvo obezbediti izolaciju podataka (Sekcija 10.2), tek onda ukljuciti paralelizam.

16.10 TFVC vs. Git — changeset, shelveset, gated check-in

Ako tim koristi TFVC (Team Foundation Version Control) umesto Git-a — na sta ukazuju termini kao sto su changeset, check-in i merge izmedju grana — razlike ispod su cesto pitanje, narocito uz "Gated Build" sa CV-a. Ako radite u Git-u, ovo je samo pozadina.

PojamGitTFVC
ModelDistribuirani — svako ima kompletnu istoriju lokalno.Centralizovani — istorija je na serveru, lokalno postoji samo workspace.
Jedinica promeneCommit (hash).Changeset (sekvencijalni numericki ID; check-in je atomican — ili prodje sve ili nista).
Preuzimanje / slanjepull / commit + push.Get Latest / Check In.
Privremeno odlaganjestash ili privremena grana.Shelveset — pending izmene sacuvane na serveru bez check-in-a (backup, deljenje, review).
GraneJeftine i lokalne.Grana je folder na serveru; merge je eksplicitna operacija izmedju dve grane (moze i za pojedinacne changeset-ove).
Gate pre integracijeBranch policy: build validation na Pull Request-u (16.6).Gated check-in: izmene se shelve-uju, build se pokrece, a check-in se desava samo ako build prodje.
ReviewPull Request.Code review nad shelveset-om ili changeset-om.
Sekcija 16.6 opisuje Gated Build kroz Git PR. Cilj je isti i u TFVC-u — nista ne ulazi u glavnu granu dok gate ne prodje — samo je mehanizam drugaciji (gated check-in umesto branch policy-ja). Zato u gate ide samo brz, stabilan smoke set, a pun regression ostaje u nightly-ju.

# GitHub Actions — ekvivalent YAML pipeline-a iz 16.3, konceptualno identican
name: nightly-regression
on:
  schedule:
    - cron: '0 2 * * *'
jobs:
  regression:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - name: Run tests
        run: dotnet test --logger trx
      - name: Publish results
        uses: actions/upload-artifact@v4
        with: { name: test-results, path: '**/*.trx' }
Isti mentalni model kao Azure Pipelines: checkout -> setup runtime -> run tests -> publish rezultate. Ono sto se najcesce pita: "koji CI alat si koristila" nije test tvog znanja o tom alatu, vec da li razumes STA pipeline treba da radi bez obzira na sintaksu.
