DEO II — AUTOMATSKO TESTIRANJE

📚 20. Glosar✓ Procitano

⏱ ~5 min citanja

Alfabetski pregled kljucnih termina. Koristite pretragu ispod za brzo pronalazenje.

A
Acceptance CriteriaUslovi koje user story mora ispuniti da bi bio prihvacen od Product Owner-a.
Acceptance Testing (UAT)Testiranje od strane krajnjih korisnika ili PO-a sa ciljem validacije poslovnih zahteva.
Ad-hoc TestingNeformalno, bez dokumentacije i plana. Za razliku od exploratory testiranja, nema ni charter.
AgileIterativni pristup razvoju softvera sa kratkim sprintovima i kontinualnim isporukama.
AllureOpen-source alat za generisanje HTML test izvestaja sa timeline-om i screenshot integracijom.
AppiumOpen-source alat za automatizaciju mobilnih aplikacija koji koristi WebDriver protokol.
AssertionProvera da li je stvarni rezultat jednak ocekivanom. Osnova svakog automatizovanog testa.
B
BDDBehavior-Driven Development — pristup koji koristi Given/When/Then format za opis ponasanja.
Black-box TestingTestiranje bez uvida u internu implementaciju — samo ulaz i izlaz.
BlockerDefekt koji sprecava dalje testiranje ili koristenje sistema. Nema workaround-a.
BVABoundary Value Analysis — tehnika koja testira vrednosti na granicama particija.
C
CI/CDContinuous Integration / Continuous Delivery — automatizovano build, test i deploy.
Contract TestingTestiranje da li consumer i provider API imaju usaglaseni kontrakt (Pact framework).
D
Data-driven TestingIsti test scenario se izvrsava sa razlicitim skupovima ulaznih podataka.
DefectDiskrepancija izmedju stvarnog i ocekivanog ponasanja sistema.
Defect DensityBroj defekata po jedinici velicine funkcionalnosti. Metrika kvaliteta koda.
Defect LeakageProcenat defekata koji su prosli QA a nadjeni su na produkciji.
Definition of DoneLista kriterijuma koje user story mora ispuniti da bi bio proglaseni Done.
Definition of ReadyLista kriterijuma koje user story mora ispuniti pre ulaska u sprint.
E
E2E TestingEnd-to-end testiranje — simulacija kompletnog korisnickog toka kroz sistem.
Entry CriteriaUslovi koji moraju biti ispunjeni da bi faza testiranja mogla da pocne.
EPEquivalence Partitioning — tehnika koja deli ulazni skup na particije.
ErrorLjudska greska — pogresan pretpostavka ili propust developera u kodu.
Escaped DefectsDefekti koje su pronasli korisnici na produkciji. Kljucna KPI za QA tim.
Exit CriteriaUslovi cijim ispunjenjem se testiranje smatra zavrsenim.
Exploratory TestingSimultano ucenje, dizajniranje i izvrsavanje testova bez unapred definisanih koraka.
F
FailureVidljivi simptom defekta u runtime-u — sistem se ponasa drugacije od ocekivanog.
Flaky TestTest koji naizmenicno prolazi i pada bez promene koda.
G
Grey-box TestingDelimicno poznavanje internih detalja sistema. Najcesci scenario u praksi.
H
Happy PathIdealni scenario — svi ulazi su validni, korisnik radi ono sto se ocekuje.
I
IEEE 829Standard za dokumentaciju sofverskog testiranja — struktura test plana.
Integration TestingTestiranje interakcije izmedju dve ili vise komponenti sistema.
ISTQBInternational Software Testing Qualifications Board — globalna QA sertifikaciona organizacija.
K
k6Open-source alat za performance (load) testiranje. Skripte se pisu u JavaScript-u.
L
Load TestingPerformance testiranje na ocekivanom normalnom opterecenju sistema.
M
MockZamena realne zavisnosti koja verifikuje i kako je pozvana, ne samo sta vraca.
N
NewmanCLI alat za pokretanje Postman kolekcija u CI/CD pipeline-u.
NUnit.NET test framework koji se koristi sa Selenium C# za pisanje i pokretanje testova.
P
Page Object ModelDesign pattern koji enkapsulira UI lokatore i interakcije za stranicu u posebnu klasu.
Pairwise TestingTehnika koja smanjuje broj test kombinacija pokrivanjem svih parova parametara.
PIIPersonally Identifiable Information — licni podaci koji se moraju anonimizovati u testovima.
PriorityHitnost korekcije defekta sa poslovnog aspekta (High/Medium/Low).
Q
QAQuality Assurance — proaktivni proces poboljsavanja procesa da bi se sprecilo nastajanje defekata.
QCQuality Control — reaktivna aktivnost pronalazenja defekata u gotovom proizvodu.
R
RACIMatrica odgovornosti: Responsible, Accountable, Consulted, Informed.
Regression TestingProvera da nove izmene nisu narusile postojecu funkcionalnost.
RESTRepresentational State Transfer — arhitekturalni stil za dizajn web API-ja.
RetestingPonovo izvrsavanje konkretnog TC koji je prethodno failovao, nakon bugfix-a.
Risk-based TestingPrioritizacija testova na osnovu verovatnoce i uticaja potencijalnog defekta.
RTMRequirements Traceability Matrix — tabela koja mapira zahteve na test case-ove i defekte.
S
Sanity TestingFokusirana verifikacija konkretne promene bez punog regression run-a.
SDETSoftware Development Engineer in Test — QA koji pise produkcioni kod i framework.
SeleniumOpen-source framework za automatizaciju web browser-a.
SeverityTehnicki uticaj defekta na sistem (Blocker/Critical/Major/Minor/Trivial).
Smoke TestingPovrsinska provera kriticnih funkcionalnosti — Go/No-Go odluka za dalji QA.
SpyOmotac oko realne implementacije koji belezi pozive za naknadnu verifikaciju.
State Transition TestingTehnika koja modelira ponasanje sistema kao skup stanja i prelaza izmedju njih.
Static TestingTestiranje bez izvrsavanja softvera — code review, inspekcija dokumentacije.
Stress TestingPerformance testiranje sistema iznad normalnog kapaciteta.
StubLazna implementacija koja vraca predefinisani odgovor bez logike.
System TestingTestiranje celokupnog sistema kao jedinstvene celine prema zahtevima.
T
Test BasisSve sto se koristi kao osnova za dizajn test case-ova: zahtevi, kod, standardi.
Test CaseDokumentovan skup koraka, ulaznih podataka i ocekivanih rezultata.
Test CoverageProcenat test basis-a (zahteva, koda, funkcionalnosti) pokriven testovima.
Test HarnessInfrastruktura koja podrzava izvrsavanje testova: runner, stubs, drivers, konfiguracija.
Test OracleMehanizam kojim se odredjuje da li je rezultat testa ispravan.
Test PlanDokument koji definise scope, pristup, resurse i raspored testiranja.
Three AmigosSesija izmedju PO, developera i QA-a pre razvoja feature-a za razjasnjavanje zahteva.
U
UATUser Acceptance Testing — testiranje od strane krajnjih korisnika ili Product Owner-a.
Unit TestingTestiranje individualne funkcije ili metode u izolaciji.
V
V-ModelSDLC model koji eksplicitno mapira svaku razvojnu fazu na odgovarajuci nivo testiranja.
ValidationProvera da li sistem ispunjava stvarne potrebe korisnika.
VerificationProvera da li je sistem izradjen u skladu sa specifikacijom.
W
WCAGWeb Content Accessibility Guidelines — standard za pristupacnost web sadrzaja.
WebDriverW3C standard protokol koji Selenium koristi za komunikaciju sa browser-om.
White-box TestingTestiranje sa punim uvidom u internu implementaciju — kod, arhitekturu, logiku.
X
XPathJezik za navigaciju kroz XML/HTML dokument — jedan od Selenium lokator tipova.

⚡ Quick Reference

Severity nivoi

BlockerSistem se ne moze koristiti. Testiranje je blokirano. Nema workaround-a.Sistem ne radi, nema workaround-a
CriticalKriticna funkcionalnost je slomljena. Korisnik ne moze da dovrsi kljucni task.Kriticna funkcionalnost slomljena
MajorZnacajna funkcionalnost ostecena. Workaround postoji ali je neudoban.Znacajna funkcionalnost ostecena
MinorManja funkcionalnost ostecena. Prihvatljiv workaround postoji.Manja funkcionalnost, postoji workaround
TrivialEstetski problem — UI, tekst, formatiranje. Nema funkcionalnog uticaja.Estetski problem, bez funkcionalnog uticaja

HTTP status kodovi

200 OKUspesno obradjen zahtev. Vraca se za GET i za akcije koje ne kreiraju resurs.Uspesno
201 CreatedResurs je kreiran. Vraca se za uspesni POST. Obicno ukljucuje Location header.Resurs kreiran (POST)
401Token nedostaje ili je neispravan. Klijent treba da se autentifikuje.Nedostaje token
403Autentifikacija je ok, ali korisnik nema prava na ovaj resurs.Token validan, nema dozvolu
404Resurs ne postoji na ovoj URL-i.Resurs ne postoji
422Format zahteva je ok, ali semanticki nije validan (narusena biznis pravila).Semanticki nevalidan zahtev
500Greska na serveru. Uvek je defekt — developer mora da je ispravi.Greska na serveru — uvek defekt

Selenium exception-i

NoSuchElementElement nije pronadjen u DOM-u. Proveriti lokator i dodati Explicit Wait.Proveriti lokator + dodati Wait
StaleElementElement pronadjen ali DOM se promenio pre interakcije. Re-locate element.Re-locate element
NotInteractableElement postoji ali je skriven, disabled ili prekriven drugim elementom.Cekati na clickability
ClickInterceptedDrugi element (modal, overlay) prekriva ciljni element pri kliku.Sacekati da overlay nestane
TimeoutExplicit Wait nije pronasao ocekivani uslov u zadatom vremenskom okviru.Povecati timeout / proveriti lokator

Smoke / Sanity / Regression

SmokeBroad + Shallow. Pokrece se na svakom novom build-u. Go/No-Go odluka za dalji QA.Broad + Shallow · svaki build
SanityNarrow + Deep. Pokrece se nakon specificnog bugfix-a ili nove funkcionalnosti.Narrow + Deep · nakon fix-a
RegressionBroad + Deep. Pokrece se pre svakog release-a. Pokriva ceo scope.Broad + Deep · pre release-a
RetestingPonovo se izvrsava konkretan TC koji je prethodno failovao, nakon bugfix-a.Konkretan TC koji je failovao
