🐧 17. Linux osnove za QA✓ Procitano

⏱ ~3 min citanja

Enterprise CI/CD agenti i deployment okruzenja su cesto Linux masine — poznavanje osnovnih komandi je korisno za debugovanje pipeline-a i provere okruzenja bez oslanjanja na DevOps tim za svaku sitnicu.

17.1 Logovi i pretraga

grep -i "error" /var/log/app.log     # trazi "error" bez obzira na velika/mala slova
tail -f /var/log/app.log             # prati log u realnom vremenu (novi redovi odmah vidljivi)
tail -f log.txt | grep -i "error"    # filtrira live log samo na greske
cat / head / tail / wc -l            # citanje fajla / pocetak / kraj / broj redova
find / -name "*.log"                 # pronadji sve .log fajlove na sistemu

17.2 Procesi i servisi

ps aux | grep service_name    # da li servis/proces radi
systemctl status service_name # status servisa (running/failed/stopped)
top / htop                    # procesi uzivo, CPU/RAM po procesu

17.3 Resursi i dozvole

df -h            # slobodan prostor na disku (cest uzrok "environment down" incidenata)
free -h          # iskoriscenost memorije
chmod 755 script.sh   # owner: read+write+execute, ostali: read+execute
Cest scenario: CI pipeline pocne da failuje bez promene u kodu — pre nego sto se sumnja na test, proveriti df -h (disk pun na agentu) i systemctl status za servise od kojih pipeline zavisi (baza, mock servisi).

17.4 SSH i rad na udaljenom agentu

ssh user@ci-agent-01                     # konekcija na udaljenu masinu (npr. Linux CI agent)
ssh -i ~/.ssh/id_rsa user@host           # sa konkretnim privatnim kljucem
scp report.trx user@host:/tmp/           # kopiranje fajla NA udaljenu masinu
scp user@host:/var/log/app.log ./       # kopiranje fajla SA udaljene masine (npr. logovi za analizu)
Tipican scenario: test padne samo na CI agentu, ne lokalno (videti Sekciju 23). SSH na agenta i provera logova/resursa direktno na masini je prvi korak pre nego sto se sumnja na sam test kod.

17.5 Environment varijable

export BASE_URL="https://qa.plm.com"     # postavljanje env varijable za trenutnu sesiju
echo $BASE_URL                           # ispis vrednosti
printenv | grep -i base                  # pretraga svih env varijabli koje sadrze "base"
env BASE_URL=https://staging.plm.com dotnet test   # override samo za jednu komandu
Direktna veza sa Sekcijom 15.4 (Secrets i environment variables u Azure DevOps) — Variable Groups u ADO se na agentu na kraju materijalizuju kao env varijable koje pipeline korak cita ovako.

17.6 Docker osnove za QA

Selenium Grid, izolovani test environment-i i CI agenti se sve cesce pokrecu kao Docker kontejneri — korisno je razumeti osnovne komande i bez da si DevOps.

docker psLista pokrenutih kontejnera — provera da li Selenium Grid/mock servis uopste radi.
docker logs -f container_namePrati logove kontejnera uzivo — prvi korak kad test ne moze da se poveze na servis.
docker exec -it container_name bashOtvara shell UNUTAR kontejnera — za direktnu inspekciju (fajlovi, procesi) bez da se kontejner rusi.
docker restart container_nameRestart kontejnera — cest brzi fix kad je servis "zaglavljen".
// Selenium Grid u Docker-u — tipicna postavka za paralelno izvrsavanje
docker run -d -p 4444:4444 --shm-size=2g selenium/standalone-chrome

// Test se povezuje na Grid umesto lokalnog drajvera
var driver = new RemoteWebDriver(new Uri("http://localhost:4444/wd/hub"), options);

17.7 Cron — planiranje automatskih run-ova

# Format: minut sat dan-u-mesecu mesec dan-u-nedelji komanda
0 2 * * *      /scripts/run-nightly-regression.sh   # svaki dan u 02:00
*/15 * * * *   /scripts/health-check.sh             # svakih 15 minuta
0 6 * * 1-5    /scripts/smoke-test.sh               # radnim danima u 06:00

crontab -l     # prikaz trenutno zakazanih job-ova
crontab -e     # izmena zakazanih job-ova
U praksi nightly regression u enterprise timovima cesce ide preko Azure DevOps scheduled trigger-a (Sekcija 16) nego preko cron-a direktno — ali ako pipeline agent sam nesto zakazuje lokalno (npr. cleanup skriptu), ovo je mehanizam.

17.8 Mrezne komande — brza dijagnostika

curl -I https://qa.plm.com/api/health     # brza provera da li API endpoint uopste odgovara (samo headeri)
curl -X POST https://api/.../login -d '{"user":"qa"}' -H "Content-Type: application/json"
ping qa.plm.com                           # da li je host dostupan na mrezi
ss -tulpn | grep 4444                     # koji proces slusa na portu 4444 (npr. Selenium Grid)
Cest prvi korak kad automatizovani test ne moze da se poveze ni na sta: curl istog endpoint-a rucno iskljucuje da li je problem u mrezi/servisu ili u samom test kodu.
