DEO I — MANUALNO TESTIRANJE

📖 1. Osnove i terminologija

⏱ ~5 min

1.1 Error, Defect, Failure — precizna razlika

Error je ljudska greska — pogresna pretpostavka, nedostatak razumevanja zahteva, ili propust developera. Postoji iskljucivo u glavi ili u kodu, nije jos vidljiva u sistemu.

Defect (Bug) je materijalizovani error — error koji je usao u kod ili dokumentaciju. Sistem sadrzi defekt, ali korisnik ga mozda jos nije susreo.

Failure je vidljivi simptom defekta u runtime-u — sistem se ponasa drugacije od ocekivanog. Svaki failure je posledica defekta, ali nije svaki defekt odmah failure (moze biti u dead code-u).

Developer pogresno razume zahtev          ->  Error
         |
Pise pogresan kod koji ulazi u sistem     ->  Defect
         |
Korisnik ili test pogodi taj code path    ->  Failure

Kada prijavis bug, prijavis Failure (sta si video).
Defect je ono sto developer ispravi u kodu.

1.2 Verification vs. Validation

VerificationDa li gradimo stvar kako treba? Staticna aktivnost — radi se bez izvrsavanja softvera: code review, design review, inspekcija dokumentacije.
ValidationDa li gradimo pravu stvar? Dinamicna aktivnost — izvrsava se softver: UAT, beta testiranje, demo sa korisnikom.
Moze se desiti da sistem prodje Verification (tacno implementuje specifikaciju) ali padne Validation — specifikacija je bila pogresna. Oba su odgovornost QA-a da pokrije.

1.3 Quality Assurance vs. Quality Control

QC — Quality ControlReaktivan — pronalazi defekte u gotovom ili polu-gotovom proizvodu. Fokus je na proizvodu. Izvrsavanje test case-ova, prijava bugova.
QA — Quality AssuranceProaktivan — popravljanje procesa da bi se sprecilo nastajanje defekata. Fokus je na procesu. Definisanje standarda, test strategije, process review.

1.4 Static vs. Dynamic testiranje

Static testiranjeSoftver se ne izvrsava. Analizira se artefakt direktno: kod, dokumentacija, zahtevi. Alati: linters, SonarQube, peer review.
Dynamic testiranjeSoftver se izvrsava sa odredjenim ulazima i posmatraju se izlazi. Sve sto zovemo 'testiranjem' u svakodnevnom smislu.

1.5 7 ISTQB principa testiranja

PrincipObjasnjenje
1. Testiranje pokazuje prisustvo defekataNe mozes reci da softvera nema gresaka. Mozes samo reci koliko si gresaka nasao.
2. Iscrpno testiranje nije moguceKombinatoricka eksplozija — broj mogucih ulaza je prakticno beskonacan. Resenje: risk-based prioritizacija.
3. Rano testiranje stedi novacBoehm-ova kriva: $1 u requirements, $10 u dizajnu, $100 u implementaciji, $1000 nakon deploymenta.
4. Grupisanje defekata (Pareto)80% defekata je u 20% modula — stari, kompleksni, cesto menjani moduli bez testova.
5. Paradoks pesticidaIsti set testova vremenom prestaje da hvata nove defekte. Resenje: redovni review i prosirenje suite-a.
6. Testiranje zavisi od kontekstaNije isti pristup za pacemaker software i za marketing landing page.
7. Odsustvo gresaka je zabludaSistem koji nema bugove ali ne resava pravi problem — ne prolazi. Validation je jednako vazna kao Verification.

2.2 V-Model

V-Model je prosirenje waterfall SDLC-a koje eksplicitno mapira svaku razvojnu fazu na odgovarajuci nivo testiranja.

  Requirements        <---------------------->  Acceptance Testing (UAT)
      System Design   <----------------->  System Testing
          Architecture<-------------->  Integration Testing
              Coding  <----------->  Unit Testing

  Kljucna vrednost: test case-ovi za visi nivo se pisu
  u odgovarajucoj razvojnoj fazi — ne ceka se kraj projekta.

2.3 Shift-Left testiranje

Shift-left znaci pomeranje QA aktivnosti sto ranije u SDLC-u.

  • QA ucestuje u requirements review-u i refinementu, ne tek kad feature bude gotov.
  • Test case-ovi se pisu paralelno sa razvojem, ne nakon.
  • Static analiza i code review su deo procesa od prvog dana.
  • Defekti u zahtevima se hvataju pre nego sto developer napise liniju koda.
Cena korekcije defekta eksponencijalno raste kako projekat odmice (Boehm-ova kriva). Defekt u zahtevima uhvacen na refinementu kosta par minuta razgovora. Isti defekt na produkciji kosta hotfix, deployment i komunikaciju sa korisnicima.

2.5 Entry i Exit Criteria — zasto su bitni

Entry i exit criteria nisu birokratija — to su dogovori koji stite QA tim.

🎯 4. Tehnike dizajniranja TC

⏱ ~5 min

4.1 Equivalence Partitioning (EP)

Deli ulazni skup na particije unutar kojih se sistem ponasa identicno. Testira se jedan reprezentativni element iz svake particije — i validnih i nevalidnih.

Primer: Polje 'Godine' — validno: 18-65

  Particija 1 — ispod minimuma (nevalidna):  vrednost 10
  Particija 2 — validni opseg:               vrednost 30
  Particija 3 — iznad maksimuma (nevalidna): vrednost 80

Umesto testiranja svakog broja od 1 do 100, dovoljno su 3 test case-a.

4.2 Boundary Value Analysis (BVA)

Defekti se statisticki najcesce javljaju na granicama particija — off-by-one greske. BVA testira na granici, jedan ispod i jedan iznad.

Primer: Polje 'Godine' — validno: 18-65
  17  ->  nevalidno  (jedan ispod donje granice)
  18  ->  validno    (donja granica)
  19  ->  validno    (jedan iznad donje granice)
  64  ->  validno    (jedan ispod gornje granice)
  65  ->  validno    (gornja granica)
  66  ->  nevalidno  (jedan iznad gornje granice)

4.3 Decision Table Testing

Koristi se kada postoje kombinacije uslova koji rezultiraju razlicitim akcijama. Svaka kolona tabele je jedan test case.

Primer: Popust na osnovu statusa i iznosa narudzbine

  Uslov                     | TC1 | TC2 | TC3 | TC4
  ---------------------------------------------------
  Premium clan              |  Y  |  Y  |  N  |  N
  Iznos > 5000 RSD          |  Y  |  N  |  Y  |  N
  ---------------------------------------------------
  Popust 20%                |  X  |     |     |
  Popust 10%                |     |  X  |  X  |
  Bez popusta               |     |     |     |  X

4.4 State Transition Testing

Modelira ponasanje sistema kao skup stanja i prelaza izmedju njih.

  [Draft] -> [Submitted] -> [Approved] -> [Shipped] -> [Delivered]
                  |               |
            [Cancelled]      [Rejected]

  Testirati: svaki validni prelaz + pokusaj nevalidnog prelaza (Draft -> Shipped direktno)

4.5 Pairwise / All-pairs testiranje

Resava problem kombinatoricke eksplozije kada imas vise parametara. Statisticki, vecina defekata se manifestuje pri interakciji dva parametra, ne svih N.

  OS: Windows, macOS, Linux  (3 vrednosti)
  Browser: Chrome, Firefox, Safari  (3 vrednosti)
  Jezik: EN, DE, FR  (3 vrednosti)

  Sve kombinacije:  3 x 3 x 3 = 27 test case-ova
  Pairwise:         ~9 test case-ova uz visoku stopu detekcije

4.6 Error Guessing

Iskustvena tehnika — QA na osnovu domain znanja pogadja gde su defekti najverovantniji. Nije zamena za formalne tehnike, dopuna je.

  • Prazna polja i null vrednosti.
  • Specijalni karakteri i unicode u text input-ima.
  • Maksimalna duzina stringa (ponasanje na 256+ karaktera).
  • Duplikati (isti email pri registraciji).
  • Istovremene akcije (double-click na submit).
  • Expired session tokom popunjavanja forme.

📝 5. Pisanje test case-ova

⏱ ~5 min

5.1 Struktura profesionalnog test case-a

IDJedinstven identifikator (TC-001, LOGIN-TC-003). Koristiti prefiks modula.
TitleKoncizan naziv koji opisuje STA se testira i POD KOJIM USLOVOM. Ne 'Test login'.
PriorityHigh / Medium / Low — utice na redosled izvrsavanja.
PreconditionsStanje sistema, podaci i okruzenje koji moraju biti ispunjeni pre pocetka.
Test DataKonkretne vrednosti koje se koriste (email, password, iznos).
StepsNumerisani, atomski koraci — svaki korak = jedna akcija.
Expected ResultPrecizno definisano ponasanje sistema. Mora biti verifikabilno i nedvosmisleno.
Actual ResultPopunjava se tokom izvrsavanja. Prazno dok se ne izvrsi.
StatusPass / Fail / Blocked / Skipped.

5.2 Status — razlika Blocked vs Skipped

PassTest case je izvrsen i sistem se ponasa kako je definisano u Expected Result-u.
FailTest case je izvrsen i sistem se NE ponasa kako je definisano. Defekt se prijavljuje.
BlockedNije moglo da se izvrsi zbog spoljne prepreke: environment pao, blocker bug, test podaci nisu pripremljeni. Nije QA odluka.
SkippedSvesna odluka da se TC ne izvrsi: out of scope, deferred. QA ili lead donosi odluku svesno.

5.3 Title — kako pisati

Format koji uvek radi: [Akcija] + [Uslov/Ulaz] + [Ocekivani ishod].

Lose:
  'Test login'  |  'Ne radi'  |  'Problem sa formom'

Dobro:
  'Login sa validnim kredencijalima preusmjerava korisnika na dashboard'
  'Login sa pogresnim passwordom prikazuje error poruku'
  'Login sa praznim email poljem prikazuje validacionu gresku'

5.4 Happy path, edge case, negative path

Happy pathIdealni scenario, sve je validno, korisnik radi tacno ono sto se ocekuje. Mora uvek biti pokriven.
Edge caseGranicna vrednost ili ekstremni uslov koji je tehnicki validan ali neuobicajen: maksimalni unos, prazna lista, 10.000 elemenata.
Negative pathNevalidni ulazi i neocekivane akcije: pogresni tipovi podataka, nedostajuca obavezna polja, akcije bez dozvola.

5.5 Granularnost — kada deliti, kada spajati

Kada DELITI:

  • Svaki korak ima sopstveni expected result koji je bitan sam po sebi.
  • Fail jednog dela ne znaci nuzno fail celog flowa.
  • Razliciti TC-ovi imaju razlicite preconditions ili test podatke.

Kada SPAJATI:

  • Koraci su strogo sekvencijalni i bez prethodnog nema smisla testirati sledeci.
  • Radi se o end-to-end flow verifikaciji (npr. celokupan checkout proces kao smoke TC).

5.6 RTM — Requirements Traceability Matrix

RTM mapira zahteve na test case-ove i defekte. Omogucava odgovor na pitanje: 'Koji zahtevi su pokriveni testovima i koji imaju otvorene defekte?'

          |                             | TC-003,TC-004  |             |
REQ-002   | Reset passworda             | TC-010, TC-011 | Pass        | -

6.5 Bug Triage

Bug triage je proces evaluacije i prioritizacije prijavljenih defekta. Odrzava se redovno — obicno jednom po sprintu ili nedeljno.

7.3 Risk-based testing

Risk Score = Probability of Failure x Business Impact

  Visok rizik   ->  testirati prvo i najdetaljnije
  Srednji rizik ->  standardna pokrivenost
  Nizak rizik   ->  smoke level ili izostaviti

Faktori visokog rizika:

  - Kriticna funkcionalna oblast (payment, auth, data migration)

🤖 11. Uvod u automatizaciju

⏱ ~5 min

11.1 Kada automatizovati, kada ne

Dobri kandidati:

  • Regression testovi koji se izvrsavaju cesto — svaki sprint ili svaki build.
  • Smoke i sanity testovi koji blokiraju dalji rad ako failuju.
  • Testovi sa velikim brojem iteracija podataka (data-driven scenariji).
  • Repetitivni, vremenski intenzivni manuelni testovi.
  • Cross-browser i cross-platform testovi.

Losi kandidati:

  • Jednokratni testovi ili scenariji koji se retko izvrsavaju.
  • Exploratory testiranje — zahteva kognitivni rad i adaptaciju.
  • UI testovi na veoma nestabilnom UI-u sa cestim layout promenama.
  • Feature koji ce se menjati u sledecoj iteraciji.

11.2 ROI automatizacije

Breakeven = Vreme pisanja / Manuelno vreme po run-u

  Primer: Manuelno 2h, Pisanje 8h -> Breakeven = 4 run-a
  Pokretanje jednom mesecno -> isplati se (breakeven za 4 meseca).
  Pokretanje jednom godisnje -> ne isplati se.
Odrzavanje je skriveni trosak koji se najcesce podcenjuje — nestabilan UI, promene lokatorima, refaktoring aplikacije. Senior QA mora da ga ukljuci u procenu od pocetka.

11.3 Test automation piramida i trofej

Piramida (Mike Cohn):
            ^
           /E2E/           <- Mali broj, sporiji
          /Integra/         <- Srednji nivo, API testovi
         /  Unit   /        <- Najveci broj, brzi

Trofej (Kent C. Dodds):
            ^
           /E2E/            <- Malo (kriticni happy path)
          /Integra/          <- Najveci deo
         /  Unit  /          <- Manje nego u piramidi
        / Static  /          <- TypeScript, linting
Anti-pattern — Ice Cream Cone: mnogo E2E testova, malo unit testova. Testovi su spori, krhki i skupi za odrzavanje.

11.4 Flaky testovi — uzroci i strategije

Najcesti uzroci:

  • Hardkodovana cekanja (Thread.Sleep) umesto Explicit Wait.
  • Zavisnost od redosleda izvrsavanja testova.
  • Race condition — test je brzi od UI-ja ili API-ja.
  • Dinamicki lokatori koji se menjaju izmedju run-ova.

Strategije resavanja:

  • Izolovati flaky testove odmah — oznaciti tagom, ne ignorisati.
  • Analizirati failure pattern — pada li samo u CI, samo u odredjeno vreme?
  • Retry logika samo za infrastrukturne greske, ne za legitimne failove.
  • Svaki flaky test tretirati kao bug — uci u backlog.

11.5 Mock, Stub i Spy — razlika

StubLazna implementacija koja vraca predefinisani odgovor. Ne verifikuje kako je pozvana — samo zamenjuje zavisnost.
MockVerifikuje i kako je pozvana: koliko puta, sa kojim argumentima. Ako ocekivanje nije ispunjeno, test pada.
SpyOmotac oko realne implementacije. Poziva pravu metodu, ali belezi pozive za naknadnu verifikaciju.
// Stub — vraca vrednost, ne proverava poziv
var stub = new Mock();
stub.Setup(p => p.Charge(It.IsAny())).Returns(new Result { Success = true });

// Mock — verifikuje da je metoda pozvana tacno jednom
var mock = new Mock();
mock.Setup(p => p.Charge(99.99m)).Returns(new Result { Success = true });
// ... izvrsiti kod ...
mock.Verify(p => p.Charge(99.99m), Times.Once);

13.1 Sta je POM i zasto postoji

Page Object Model je design pattern koji enkapsulira UI lokatore i interakcije za odredjenu stranicu u posebnu klasu. Test kod komunicira sa stranicom iskljucivo kroz metode te klase — nikad direktno sa lokatorima.

  • Separacija brige — lokatori i UI logika odvojeni od test logike.
  • Odrzivost — promena lokacije elementa zahteva izmenu samo u Page klasi.
  • Citljivost — testovi opisuju ponasanje, ne implementacione detalje.
  • Ponovna upotreba — iste metode se koriste u vise testova.

15.5 Best practices za testove u CI/CD-u

  • Testovi moraju biti deterministicki — isti ulaz, isti rezultat uvek.
  • Paralelizacija: grupisati testove da se izvrsavaju paralelno.
  • Flaky testovi moraju biti izolovani i oznaceni, ne ignorisani.

  • Cuvati screenshots i logove samo za failovane testove.

16.6 Pre-commit checklist za automatizovani test
