23.1 Zasto SQL za QA

UI i API ti pokazuju sta aplikacija tvrdi da se desilo. Baza ti pokazuje sta se stvarno desilo. Veliki deo ozbiljnog testiranja je upravo taj jaz: sacuvas zapis kroz UI, dobijes zeleni toast "Saved", a u bazi je polje ostalo null, status se nije promenio, ili je upisan duplikat. Bez SQL provere taj bag prolazi jer je UI asercija zadovoljena.

Za QA, SQL se koristi u cetiri tipicne situacije: provera stanja posle UI/API akcije (da li je upis tacan), priprema test podataka (naci ili napraviti zapis koji zadovoljava preduslov), debug (zasto je test pao — sta je u bazi u tom trenutku), i reconciliation (da li API odgovor odgovara izvoru istine u bazi). Ne treba ti DBA nivo — treba ti pouzdan SELECT, JOIN-ovi, agregacije i svest o zamkama izmedju baza.

U PLM / enterprise domenu podaci su povezani kroz vise tabela (stavka, verzija, atribut, veza, audit log). "Da li je sacuvano" skoro nikad nije jedna tabela — zato su JOIN-ovi (23.3) i provera posle akcije (23.5) centralne vestine, ne SELECT * nad jednom tabelom.

23.2 SELECT osnove za proveru podataka

Redosled izvrsavanja nije redosled pisanja. Pises SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY, ali baza logicki radi FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Zato alias iz SELECT-a ne mozes koristiti u WHERE (jos ne postoji), ali mozes u ORDER BY.

-- Naci zapis koji si upravo sacuvao kroz UI
SELECT id, name, status, modified_on, modified_by
FROM item
WHERE name = 'TEST-ITEM-042'
  AND status IN ('Draft', 'In Review')
  AND modified_on >= '2026-11-12'
ORDER BY modified_on DESC;

Filteri koji se stalno koriste u QA proverama: IS NULL / IS NOT NULL (nikad = NULL — vratice prazan skup jer je NULL "nepoznato", ne vrednost), LIKE 'TEST-%' za prefiks test podataka, BETWEEN za opsege, IN (...) umesto gomile OR-ova. Uvek stavi ORDER BY kad proveravas "poslednji" zapis — bez njega redosled nije garantovan.

NULL se siri kroz izraze: WHERE discount <> 0 NE vraca redove gde je discount NULL, iako NULL ocigledno nije 0. Ako proveravas "sve sto nije 0", moras eksplicitno: WHERE discount <> 0 OR discount IS NULL. Ovo je cest izvor laznih "nema rezultata" u QA proverama.

23.3 JOIN-ovi — povezivanje tabela

INNER JOIN vraca samo redove koji imaju par u obe tabele. LEFT JOIN vraca sve iz leve tabele, a NULL gde nema para desno. Za QA je LEFT JOIN cesto vredniji: njime hvatas sta nedostaje.

-- Stavke koje NEMAJU nijednu verziju (sirocici posle bag-a u kreiranju)
SELECT i.id, i.name
FROM item i
LEFT JOIN item_version v ON v.item_id = i.id
WHERE v.id IS NULL;

Taj WHERE desna_tabela.id IS NULL posle LEFT JOIN-a je klasican "anti-join" obrazac — nalazi redove bez para. Koristan za: stavke bez obaveznog atributa, korisnike bez role, narudzbine bez stavki.

Uslov na desnu tabelu LEFT JOIN-a ne sme u WHERE ako hoces da zadrzis sve leve redove — WHERE se primenjuje posle join-a i izbacuje NULL redove, cime LEFT JOIN postaje INNER. Takav uslov ide u ON: LEFT JOIN item_version v ON v.item_id = i.id AND v.is_latest = 1. WHERE na desnoj tabeli koristis namerno samo za anti-join (IS NULL).

23.4 Agregacije i otkrivanje duplikata

COUNT, SUM, MIN/MAX uz GROUP BY su alat broj jedan za data-integrity provere. Najcesca: da li postoje duplikati tamo gde ne bi smeli.

-- Duplikati po poslovnom kljucu (treba da bude jedinstven)
SELECT name, COUNT(*) AS cnt
FROM item
GROUP BY name
HAVING COUNT(*) > 1
ORDER BY cnt DESC;

Razlika koju pitaju na intervjuu: WHERE filtrira redove pre grupisanja, HAVING filtrira grupe posle. "Nadji imena sa vise od jednog zapisa" je po definiciji uslov nad grupom → HAVING. I pazi: COUNT(*) broji redove ukljucujuci NULL, COUNT(kolona) ignorise NULL u toj koloni — razlika koja menja rezultat.

23.5 Provera stanja baze posle UI/API akcije

Ovo je najvredniji obrazac u celoj sekciji. Automatizovani test cesto proverava samo da se pojavila success poruka — a to je slab dokaz. Jaka asercija proverava na dva nivoa: UI stanje posle refresh-a i vrednost u bazi.

// C# — posle Save akcije u UI, potvrdi u bazi (Dapper/ADO.NET)
// Ne proveravaj samo toast "Saved" — proveri izvor istine.
string sql = @"SELECT status FROM item WHERE id = @id";
var statusInDb = connection.QuerySingleOrDefault<string>(sql, new { id = itemId });

Assert.Equal("In Review", statusInDb);   // DB je stvarno azuriran
// + UI asercija posle refresh-a da se slaze sa bazom

Pravila za ovaj obrazac: (1) citaj bazu posle sto je akcija potvrdjena, ne u trci sa async upisom — sacekaj uslov, ne thread.sleep; (2) proveri tacno polje koje akcija menja, ne samo "red postoji"; (3) ako postoji audit/history tabela, proveri i nju (ko, kada, stara vs nova vrednost) jer tamo cesto ispliva bag koji glavna tabela sakrije.

Veza na manuelno testiranje: ista logika kao "proveri na svakom nivou" iz Sekcije 10.5. SQL provera je samo najnizi, najpouzdaniji nivo te iste piramide — ispod UI-ja i API-ja.

23.6 API-to-DB validacija

Kad testiras API (Postman/RestSharp), odgovor je ono sto servis vraca — a ne nuzno ono sto je u bazi. Reconciliation test uporedjuje to dvoje: pozovi endpoint, pa proveri da polja iz JSON odgovora odgovaraju redu u bazi. Hvata bagove gde API kesira staru vrednost, mapira pogresno polje, ili vraca izracunatu vrednost koja se razilazi sa cuvanim stanjem.

-- Posle POST /items koji vrati {"id": 5012, "status": "Draft"}
-- Potvrdi da baza stvarno drzi isto stanje:
SELECT id, status, created_on
FROM item
WHERE id = 5012;
-- Ocekivano: status = 'Draft', created_on ~ vreme poziva

Tipicni nalazi: API vraca status: "Active" a u bazi je enum 1 koji se mapira pogresno; API vraca formatiran datum a baza cuva UTC pa se razilaze za timezone; soft-delete gde API sakrije red ali is_deleted = 1 i dalje stoji u bazi (pa "obrisani" podaci curle u drugi izvestaj).

Isti SQL ne radi isto na sve tri baze. U enterprise okruzenju gde backend moze biti SQL Server ili Oracle (a dev/lokalno nekad PostgreSQL), ovo su razlike koje realno zezaju test upite:

23.8 Transakcije i test podaci

Testovi koji pisu u bazu moraju da oc(iste za sobom, inace sledeci run kreira duplikate ili pada na "vec postoji". Dve strategije: (1) setup/teardown — kreiras poznat zapis pre testa, brises ga posle; (2) rollback — sve u transakciji koja se na kraju ponisti, pa baza ostaje netaknuta.

-- Rucna provera bez trajne izmene: pokreni, pogledaj, ponisti
BEGIN TRANSACTION;

UPDATE item SET status = 'Approved' WHERE id = 5012;
SELECT status FROM item WHERE id = 5012;   -- vidi efekat

ROLLBACK;   -- vrati sve; baza kao da se nista nije desilo

Pravila higijene test podataka: koristi prepoznatljiv prefiks (TEST-, QA-) da ih lako nadjes i obrises; nikad ne diraj deljene reference podatke rucnim UPDATE-om na deljenom okruzenju; DELETE uvek sa WHERE (i proveri ga prvo kao SELECT sa istim WHERE). Na deljenoj bazi radije SELECT i rollback nego trajni UPDATE.

UPDATE/DELETE bez WHERE menja CELU tabelu. Pre svakog destruktivnog upita, pokreni isti filter kao SELECT i pogledaj koliko redova pogadja. Na deljenom QA okruzenju jedan DELETE bez WHERE je incident, ne bag.
