10.3 Dependency management — mock servisi i stubovi

Vecina modernih aplikacija zavisi od eksternih servisa: payment gateway, email servis, SMS provajder, third-party API.

PristupOpis
Sandbox / test modeProvajder nudi posebno okruzenje (Stripe, PayPal, Twilio). Ponasanje je identicno produkciji, ali nema realnih transakcija.
Mock servisInterni servis koji simulira ponasanje eksternog. Potpuna kontrola — simulirati 500 gresku, timeout, spor odgovor.
WireMock / MockServerAlati za kreiranje HTTP mock servera. Definisu se request/response parovi u JSON konfiguraciji.
Strategija: Unit/Integration = mock sve; System testing = sandbox provajdera; UAT/pre-prod = realne integracije sa test nalozima.

10.4 PII i GDPR u test podacima

  • Nikad ne kopirati produkcijske podatke bez anonimizacije.
  • Test emailovi uvek na domenu koji ne postoji u produkciji (npr. @test.internal).
  • Kartice — koristiti test brojeve koje payment provajder daje za sandbox.
  • Koristiti Faker biblioteke za generisanje realisticnih ali laznih podataka.

10.5 SQL verifikacija podataka u testiranju

SQL upiti su kriticni za verifikaciju da li je UI ili API akcija zaista izmenila podatke u bazi — ne samo da je prikazala success poruku. Ovo vazi za MSSQL, Oracle i druge relacione baze (videti Sekciju 14 za API + DB validaciju).

Seed / Setup — priprema test podataka

-- Kreiranje test korisnika pre testa
INSERT INTO Users (Email, Role, IsActive, CreatedAt)
VALUES ('qa-test@test.internal', 'QA', 1, GETDATE());

-- PLM primer: kreiranje test specifikacije sa atributima
INSERT INTO Specifications (SpecId, Title, Status, OwnerId)
VALUES ('SPEC-TEST-001', 'QA Test Material', 'Draft', @TestUserId);

INSERT INTO SpecAttributes (SpecId, AttrName, AttrValue)
VALUES ('SPEC-TEST-001', 'Material', 'Steel'),
       ('SPEC-TEST-001', 'Grade', 'A36');

Assertion — verifikacija nakon akcije

-- Posle UI/API akcije "Approve Specification", verifikovati u bazi:
SELECT Status, ApprovedBy, ApprovedDate
FROM Specifications
WHERE SpecId = 'SPEC-TEST-001';
-- Ocekivano: Status = 'Approved', ApprovedBy IS NOT NULL

-- Verifikacija kaskadnih efekata:
SELECT COUNT(*) FROM AuditLog
WHERE EntityId = 'SPEC-TEST-001' AND Action = 'StatusChange';
-- Ocekivano: >= 1 (akcija je upisana u audit trail)

Cleanup — ciscenje test podataka

-- Brisanje test podataka nakon testa (obrnut redosled od insert-a)
DELETE FROM SpecAttributes WHERE SpecId = 'SPEC-TEST-001';
DELETE FROM Specifications WHERE SpecId = 'SPEC-TEST-001';
DELETE FROM Users WHERE Email = 'qa-test@test.internal';

-- Alternativa: TRANSACTION rollback pattern
BEGIN TRANSACTION;
  -- ... seed + test akcija + assertion ...
ROLLBACK;  -- automatski cisti sve promene

C# integracija — DB assertion u automatizovanom testu

// xUnit test sa SQL verifikacijom nakon UI akcije
[Fact]
public void ApproveSpec_ShouldUpdateStatusInDatabase()
{
 var specPage = new SpecificationPage(Driver);
 specPage.NavigateTo("SPEC-TEST-001");
 specPage.ClickApprove();

 using var conn = new SqlConnection(_connectionString);
 conn.Open();
 var cmd = new SqlCommand(
  "SELECT Status FROM Specifications WHERE SpecId = @id", conn);
 cmd.Parameters.AddWithValue("@id", "SPEC-TEST-001");

 var status = (string)cmd.ExecuteScalar();
 Assert.Equal("Approved", status);
}
DB assertions otkrivaju situacije gde UI prikazuje success ali podatak nije sacuvan (ili je sacuvan pogresno). Posebno vazno za enterprise sisteme sa kompleksnim workflow-ima i audit trail-ovima.

10.6 Multi-version environment management

U enterprise sistemima isti test kod cesto trce na vise okruzenja sa razlicitim verzijama proizvoda. Upravljanje razlikama bez dupliranja testova je kljucan skill.

StrategijaOpisKada koristiti
Config per environmentURL-ovi, credentials, feature flags u odvojenim config fajlovima (appsettings.QA.json, appsettings.Staging.json).Uvek — nulti nivo izolacije.
Page Object overrideBazni Page Object + tenant/version-specific override klasa koja menja lokatore ili flow korake.Kad se UI razlikuje izmedju verzija ili tenanta.
Conditional skipTest se preskace na verziji gde feature ne postoji. Oznacava se razlogom, ne ignorise se bez objasnjenja.Retko — samo kad capability ne postoji.
Feature flags u config-uBoolean flag koji ukljucuje/iskljucuje deo test logike per environment.Kad je ista funkcionalnost razlicito implementirana.
// Primer: isti test, razliciti config-ovi
// appsettings.QA.json
{ "BaseUrl": "https://qa.plm.com", "Version": "3.1", "HasCopilot": false }

// appsettings.Staging.json
{ "BaseUrl": "https://staging.plm.com", "Version": "3.2", "HasCopilot": true }

// Test koji koristi config:
[Fact]
public void CopilotSearch_ShouldReturnResults()
{
 Skip.If(!Config.HasCopilot, "Copilot not available in this version");
 // ... test logika ...
}
Pravilo: test scenario ostaje isti, varijabilnost se apsorbuje u config-u i Page Object sloju. Ako moras duplirati test za razlicitu verziju — nesto nije dobro u arhitekturi (videti Sekciju 16).

10.7 Testiranje data extraction workflow-a

Mnoge enterprise aplikacije imaju import/export funkcionalnost — Excel upload, CSV import, field mapping. Testiranje ovih workflow-a zahteva specifican pristup:

ScenarioSta testirati
Validan fajlUpload uspeva, sva polja pravilno mapirana, podaci vidljivi u aplikaciji i bazi.
Pogresan format.txt umesto .xlsx, .csv sa pogresnim delimiterom — jasna poruka o gresci.
Prazan fajlExcel sa header-om ali bez redova — graceful handling, ne crash.
Malformed dataNumericki atribut sa tekstom, datum u pogresnom formatu, specijalni karakteri.
Field mappingExcel kolona "Material Name" mapirana na polje "Title" u aplikaciji — tacnost mapiranja.
DuplikatiUpload fajla koji sadrzi vec postojece zapise — update, skip, ili greska po biznis pravilu.
Veliki fajl10.000+ redova — performance, timeout, parcijalni import.
Submit-to-form flowImportovani podaci moraju proci validaciju pre kreiranja zapisa u sistemu.
// PLM primer: test Excel upload workflow-a
[Fact]
public void ExcelUpload_ValidFile_ShouldCreateSpecifications()
{
 var importPage = new DataImportPage(Driver);
 importPage.UploadFile("TestData/valid_specs.xlsx");
 importPage.MapColumn("Material Name", "Title");
 importPage.MapColumn("Grade", "Grade Attribute");
 importPage.ClickSubmit();

 Assert.Equal("3 specifications created", importPage.GetResultMessage());

 // DB verifikacija (videti Sekciju 10.5)
 using var conn = new SqlConnection(_connectionString);
 var count = conn.ExecuteScalar<int>(
  "SELECT COUNT(*) FROM Specifications WHERE Source = 'Excel Import'");
 Assert.Equal(3, count);
}

10.8 Environment checklist — pre pocetka testiranja

  [ ] Build je deployovan i verzija je verifikovana
  [ ] Seed data je prisutna i ispravna
  [ ] External mock servisi / sandbox su dostupni
  [ ] Test nalozi postoje i pristupni podaci su ispravni
  [ ] Baza podataka je u ocekivanom stanju (nije zaprljana)
  [ ] Konfiguracija okruzenja odgovara ocekivanoj (env vars, feature flags)
  [ ] Smoke test okruzenja prolazi pre pocetka punog test run-a
  [ ] Monitoring i logovi su dostupni za debugging
