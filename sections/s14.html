500 Internal Server ErrorGreska na serveru. Uvek defekt.
502 Bad GatewayUpstream servis ne odgovara.
503 Service UnavailableServis trenutno nedostupan.

14.3 Sta testirati na API-ju

Sta testiratiDetalj
Status kodDa li je odgovor ispravan? 200 vs. 201 vs. 400 — svaki ima specificno znacenje.
Response bodyDa li JSON odgovara ocekivanom kontraktu? Da li su sva polja prisutna?
Auth/AuthzBez tokena -> 401. Sa pogresnim pravima -> 403. Validan token -> 200.
Response timeDa li API odgovara u prihvatljivom roku? (< 2000ms)
IdempotencijaVisestruki GET/PUT/DELETE ne smeju da menjaju stanje sistema.
Schema validacijaStruktura odgovora vs. OpenAPI/Swagger kontrakt.

14.4 Postman test skripta — primeri

pm.test('Status code is 200', () => {
    pm.response.to.have.status(200);
});

pm.test('Token saved', () => {
    const token = pm.response.json().access_token;
    pm.expect(token).to.be.a('string').and.not.empty;
    pm.environment.set('auth_token', token);
});

pm.test('Response time is acceptable', () => {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

14.6 Contract testing — Pact framework

Contract testing resava problem koji se javlja u mikroservisnim arhitekturama: tim A menja API koji tim B koristi, i breaking change prolazi nezapazeno sve do produkcije.

Tok:
  1. Consumer pise pact — definise sta ocekuje od providera
  2. Pact se cuva u Pact Broker
  3. Provider verifikuje kontrakt u svom CI/CD pipeline-u
  4. Ako provider promeni API na nacin koji krsi kontrakt,
     verifikacija pada pre deploymenta

  Rezultat: breaking change je uhvacen u CI/CD, ne na produkciji.
