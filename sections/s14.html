14.4 Postman test skripta — primeri

pm.test('Status code is 200', () => {
    pm.response.to.have.status(200);
});

pm.test('Token saved', () => {
    const token = pm.response.json().access_token;
    pm.expect(token).to.be.a('string').and.not.empty;
    pm.environment.set('auth_token', token);
});

pm.test('Response time is acceptable', () => {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

14.5 RestSharp — API testiranje u C#

// GET sa deserializacijom i assertion-ima (xUnit)
[Fact]
public void GetUser_WithValidId_ShouldReturnUser()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users/1", Method.Get);
 request.AddHeader("Authorization", $"Bearer {_token}");

 var response = client.Execute<UserDto>(request);

 Assert.Equal(HttpStatusCode.OK, response.StatusCode);
 Assert.NotNull(response.Data);
 Assert.Equal("uros@test.com", response.Data.Email);
}

// POST sa JSON body-jem
[Fact]
public void CreateUser_WithValidData_ShouldReturn201()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users", Method.Post);
 request.AddJsonBody(new { Email = "new@test.com", Role = "QA" });
 request.AddHeader("Authorization", $"Bearer {_token}");

 var response = client.Execute(request);

 Assert.Equal(HttpStatusCode.Created, response.StatusCode);
 Assert.Contains("new@test.com", response.Content);
}
RestSharp je native C# HTTP klijent — prirodan izbor za API testove u istom solution-u sa Selenium testovima (videti Sekciju 16), bez prebacivanja na JavaScript/Newman.

14.7 Contract testing — Pact framework

Contract testing resava problem koji se javlja u mikroservisnim arhitekturama: tim A menja API koji tim B koristi, i breaking change prolazi nezapazeno sve do produkcije.

Tok:
  1. Consumer pise pact — definise sta ocekuje od providera
  2. Pact se cuva u Pact Broker
  3. Provider verifikuje kontrakt u svom CI/CD pipeline-u
  4. Ako provider promeni API na nacin koji krsi kontrakt,
     verifikacija pada pre deploymenta

  Rezultat: breaking change je uhvacen u CI/CD, ne na produkciji.

14.8 Auth i security testing za API

Token-based autentifikacija je standard u modernim API-jima. QA mora testirati ne samo "radi li sa validnim tokenom" nego i sve edge case-ove oko auth lifecycle-a.

ScenarioOcekivanoZasto je vazno
Zahtev bez tokena401 UnauthorizedAPI ne sme dozvoliti anonimni pristup zasticenim resursima.
Istekao token401 + jasna porukaFrontend mora znati da treba refresh, ne genericni error.
Token sa pogresnom rolom403 ForbiddenRBAC mora raditi na API nivou, ne samo na UI-ju.
Token rotationStari token prestaje da vazi nakon izdavanja novogSprecava replay napade sa ukradenim tokenom.
Session expirationSesija istice nakon definisanog perioda neaktivnostiCompliance zahtev — ne sme ostati ulogovan zauvek.
Concurrent sessionsPo policy-ju: dozvoliti ili blokirati drugu sesijuEnterprise aplikacije cesto ogranicavaju na jednu sesiju.
// RestSharp — test za istekao token (xUnit)
[Fact]
public void ExpiredToken_ShouldReturn401()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users", Method.Get);
 request.AddHeader("Authorization", $"Bearer {_expiredToken}");

 var response = client.Execute(request);

 Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
}

// Test za RBAC — viewer ne sme moci da brise
[Fact]
public void ViewerRole_DeleteUser_ShouldReturn403()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users/1", Method.Delete);
 request.AddHeader("Authorization", $"Bearer {_viewerToken}");

 var response = client.Execute(request);

 Assert.Equal(HttpStatusCode.Forbidden, response.StatusCode);
}
RBAC testiranje na API nivou je kriticno — cesto se desava da UI pravilno sakriva dugme "Delete", ali API endpoint i dalje dozvoljava brisanje ako se pozove direktno. Uvek testirati API nezavisno od UI-ja (videti Sekciju 12.8 — DevTools Network tab).
