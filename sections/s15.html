15.4 Postman test skripta — primeri

pm.test('Status code is 200', () => {
    pm.response.to.have.status(200);
});

pm.test('Token saved', () => {
    const token = pm.response.json().access_token;
    pm.expect(token).to.be.a('string').and.not.empty;
    pm.environment.set('auth_token', token);
});

pm.test('Response time is acceptable', () => {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

15.5 RestSharp — API testiranje u C#

// GET sa deserializacijom i assertion-ima (xUnit)
[Fact]
public void GetUser_WithValidId_ShouldReturnUser()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users/1", Method.Get);
 request.AddHeader("Authorization", $"Bearer {_token}");

 var response = client.Execute<UserDto>(request);

 Assert.Equal(HttpStatusCode.OK, response.StatusCode);
 Assert.NotNull(response.Data);
 Assert.Equal("uros@test.com", response.Data.Email);
}

// POST sa JSON body-jem
[Fact]
public void CreateUser_WithValidData_ShouldReturn201()
{
 var client = new RestClient("https://api.myapp.com");
 var request = new RestRequest("/users", Method.Post);
 request.AddJsonBody(new { Email = "new@test.com", Role = "QA" });
 request.AddHeader("Authorization", $"Bearer {_token}");

 var response = client.Execute(request);

 Assert.Equal(HttpStatusCode.Created, response.StatusCode);
 Assert.Contains("new@test.com", response.Content);
}
RestSharp je native C# HTTP klijent — prirodan izbor za API testove u istom solution-u sa Selenium testovima (videti Sekciju 19), bez prebacivanja na JavaScript/Newman.

Gornji primer koristi anonimni objekat za POST body — radi za brz test, ali se ne skalira. U vecem suite-u se umesto toga koriste dva pattern-a: POCO klase za (de)serializaciju i Builder za kreiranje test podataka.

// Models/UserDto.cs — POCO za request/response
public class UserDto
{
    public string Email { get; set; }
    public string Role { get; set; }
    [Required]
    public string DisplayName { get; set; }
}

// Builders/UserBuilder.cs — fluent API, menja samo relevantno polje po testu
public class UserBuilder
{
    private UserDto _user = new UserDto { Email = "default@test.com", Role = "User", DisplayName = "Default User" };

    public static UserBuilder Default() => new UserBuilder();
    public UserBuilder WithRole(string role) { _user.Role = role; return this; }
    public UserBuilder WithEmail(string email) { _user.Email = email; return this; }
    public UserDto Build() => _user;
}

// Upotreba u testu — citljivo, vidi se odmah sta je za TAJ test bitno
var admin = UserBuilder.Default().WithRole("admin").Build();
var request = new RestRequest("/users", Method.Post).AddJsonBody(admin);
POCO umesto anonimnog objektaJaka tipizacija (compile-time greska umesto runtime typo-a u imenu polja), refaktorisanje bez string zamena, validacija preko atributa ([Required]), lako mapiranje na JSON schema (Sekcija 15.3).
Builder umesto konstruktora sa svim poljimaFluent API menja samo polje relevantno za taj test — UserBuilder.Default().WithRole("admin").Build() je citljivije od konstruktora sa 10 parametara gde vecina nema veze sa onim sto se testira. Kad model dobije novo polje, menja se samo Builder, ne svaki poziv konstruktora u suite-u.
Factory (kad treba)Za vrednosti koje MORAJU biti random/unikatne po pokretanju (email, timestamp) — da paralelni testovi (Sekcija 16.9) ne dele isti podatak.
Struktura u projektu: POCO klase u Models/, builderi u Builders/, factory samo za polja koja moraju biti random. Isti Builder pattern se koristi i za UI test podatke (ne samo API) — princip je identican.

15.7 Contract testing — Pact framework

Contract testing resava problem koji se javlja u mikroservisnim arhitekturama: tim A menja API koji tim B koristi, i breaking change prolazi nezapazeno sve do produkcije.

Tok:
  1. Consumer pise pact — definise sta ocekuje od providera
  2. Pact se cuva u Pact Broker
  3. Provider verifikuje kontrakt u svom CI/CD pipeline-u
  4. Ako provider promeni API na nacin koji krsi kontrakt,
     verifikacija pada pre deploymenta

  Rezultat: breaking change je uhvacen u CI/CD, ne na produkciji.

15.8 Auth i security testing za API

Token-based autentifikacija je standard u modernim API-jima. QA mora testirati ne samo "radi li sa validnim tokenom" nego i sve edge case-ove oko auth lifecycle-a.

Token sa pogresnom rolom403 ForbiddenRBAC mora raditi na API nivou, ne samo na UI-ju.

// RestSharp — test za istekao token (xUnit)
[Fact]
public void ExpiredToken_ShouldReturn401()
{
 var client = new RestClient("https://api.myapp.com");

 var response = client.Execute(request);

 Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
}

// Test za RBAC — viewer ne sme moci da brise
[Fact]
public void ViewerRole_DeleteUser_ShouldReturn403()
{

RBAC testiranje na API nivou je kriticno — cesto se desava da UI pravilno sakriva dugme "Delete", ali API endpoint i dalje dozvoljava brisanje ako se pozove direktno. Uvek testirati API nezavisno od UI-ja (videti Sekciju 13.8 — DevTools Network tab).
