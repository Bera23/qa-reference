19.2 LLM za generisanje Selenium C# test skripti

Primer prompta:

  'Ti si senior QA automation inzenjer koji pise Selenium C# testove.
   Koristi xUnit, Page Object Model i FluentAssertions.
   Generiši test klasu za sledeci scenario:

   Feature:  Forgot Password funkcionalnost
   URL:      /forgot-password
   Elementi: input[name=email], button[type=submit], .success-message

   Scenariji:
   1. Validan email -> prikazuje se success poruka
   2. Nevalidan email format -> prikazuje se validaciona greska
   3. Nepostojeci email -> prikazuje se ista success poruka (security by design)

   Koristi BasePage sa WaitForVisible metodom.
   Naming konvencija: MethodName_StateUnderTest_ExpectedBehavior'

Workflow:
  LLM generise skelet -> QA proverava lokatore -> QA dodaje specificne
  test podatke -> QA verifikuje Expected Result-e -> QA pokrecepokalno.
LLM stedi 60-70% vremena na boilerplate kodu. Generisani kod treba da prati POM strukturu (Sekcija 13) i naming konvenciju (Sekcija 16). Ostatak — domain znanje, specificnosti aplikacije, edge case-ovi — ostaje iskljucivo odgovornost QA inzenjera.

19.3 Vizuelna regresija

Applitools EyesAI-powered vizuelni testing. Koristi ML da razlikuje significantne vizuelne promene od nebitnih (anti-aliasing, font rendering razlike). Integracija sa Selenium, Cypress, Playwright.
Percy (BrowserStack)Vizuelna regresija integrisana sa CI/CD pipeline-om. Svaki PR dobija vizuelni diff review.

19.4 Granice i rizici AI u testiranju

RizikObjasnjenje
HallucinationLLM-ovi mogu generisati plausibilne ali pogresne test case-ove ili nepostojece API endpoint-e. Uvek review-ovati output.
Nedostatak kontekstaAI ne zna biznis pravila, istoriju projekta ni specificnosti sistema.

19.5 Generisanje Selenium C# koda

// LLM generisani skelet — potrebna QA revizija
public class ForgotPasswordPage : BasePage
{
 private By EmailField   => By.CssSelector(input[name=email]);
 private By SubmitButton => By.CssSelector(button[type=submit]);
 private By SuccessMsg  => By.CssSelector(.success-message);

    [Fact]
    public void ValidEmail_ShouldShowSuccessMessage()
    {
 var page = new ForgotPasswordPage(Driver);
 page.Navigate();
 page.EnterEmail("user@test.com");
 page.Submit();
 Assert.Contains("Check your email", page.GetSuccessMessage());
    }
}

19.6 Testiranje AI-powered feature-a

Kada aplikacija sama koristi AI (npr. Copilot, chatbot, AI preporuke), output je nedeterministicki — ne moze se asertovati na tacan tekst. Umesto toga, testiraju se invarijante po pet dimenzija:

DimenzijaSta se proveravaPrimer asercije
RelevantnostDa li odgovor adresira temu iz prompta?Prompt o specifikaciji materijala → odgovor sadrzi atribute tog materijala, ne genericke informacije.
GroundingDa li se odgovor oslanja na dozvoljene izvore podataka, bez fabriciranja cinjenica?Copilot navodi specifikaciju koja postoji u sistemu, ne izmisljenu.
Permission boundariesDa li AI postuje RBAC? Korisnik bez pristupa kategoriji X ne sme dobiti podatke iz nje.User sa rolom "Viewer" pita za confidential BOM → odgovor je prazan ili access denied.
Format contractDa li odgovor prati ocekivanu strukturu — obavezna polja, output shape?JSON odgovor sadrzi "source", "confidence", "text" polja.
Latency / error budgetDa li odgovor stize u okviru SLA bez fallback greske?Response time < 5s, nema generic error poruke.

Strategije za stabilno AI testiranje

  • Golden intent prompts — skup poznatih upita sa ocekivanim ponasanjem. Threshold-based pass/fail umesto egzaktnog poklapanja.
  • Negativni testovi — out-of-scope prompti koji treba da budu odbijeni, adversarial inputs, permission boundary probes gde odgovor mora biti prazan iako podaci postoje u sistemu.
  • Fiksirani kontekst — isti korisnik, ista rola, isti dataset za svaki test run. Varijabla je samo prompt.
Permission-bound testiranje je cesto najvrednije — otkriva slucajeve gde AI leak-uje podatke iz kategorija kojima korisnikova rola nema pristup. To nije hallucination problem, to je autorizacioni propust surfaced kroz AI — i klasicno testiranje ga nece uhvatiti.

19.7 AI alati u svakodnevnom QA radu

AI alati nisu samo objekat testiranja — oni su i alat koji QA koristi svaki dan za produktivnost.

AlatQA upotreba
GitHub CopilotAutocomplete za automation kod — Page Object metode, assertion patterns, boilerplate. Stedi 60-70% vremena na repetitivnom kodu (videti 19.2).
M365 CopilotAnaliza nightly failure logova — paste stack trace, pitaj za root cause. Sumarizacija dugackih bug threadova. Drafting bug reporta iz beleški.
ChatGPT / ClaudeGenerisanje test podataka, review test case design-a, objasnjavanje nepoznatog koda, brainstorming edge case-ova.

Primer: AI-assisted failure analysis

Prompt za M365 Copilot / ChatGPT:

  "Ovo je stack trace iz nightly regression testa koji je prosao
   do jucerasnjeg build-a, a sada pada:

   [StaleElementReferenceException at MaterialPage.SelectLOV()]

   Test scenario: kreiranje nove specifikacije sa Material atributom.
   Poslednji changeset na aplikaciji: refaktor LOV dropdown komponente.

   Sta je najerovatniji uzrok i koji je najbrzi fix?"

Odgovor: AI sugerise re-find pattern jer LOV re-renderuje DOM.
QA verifikuje hipotezu, implementira fix, check-in.

19.8 Custom Copilot agenti (Microsoft Agent Builder)

QA moze kreirati custom AI agente za specificne zadatke koristeci Microsoft Copilot Studio / Agent Builder — bez pisanja koda, samo sa system instructions i definisanim izvorima podataka.

AgentSystem instructionData sourceQA vrednost
Test Oracle Agent"Ti si QA ekspert za PLM sistem. Odgovaraj samo na osnovu specifikacije."Produktna dokumentacija, specifikacijaBrza verifikacija expected behavior-a bez pretrazivanja dokumenata.
Bug Triage Assistant"Klasifikuj failure u: app regresija, script issue, environment issue."Istorija nightly rezultata, poznati flaky testoviUbrzava dnevni triage — AI predlaze kategoriju, QA potvrdjuje.
Custom Agent — ključni elementi:

  System Instructions:
    - Definisi ulogu, ton, ogranicenja
    - "Odgovaraj samo na osnovu prilozenог dokumenta"
    - "Ako nemas odgovor, reci 'nije u specifikaciji'"

  Data Sources:
    - Upload dokumenata (PDF, Word, Excel)
    - SharePoint stranice
    - Web URL-ovi

  Testiranje agenta:
    - Isti 5-dimenzionalni pristup kao za AI feature (19.6)
    - Da li odgovara samo iz dozvoljenih izvora (grounding)?
    - Da li odbija pitanja van scope-a?
    - Da li multimodalni input (slika + tekst) radi ispravno?
Izgradnja custom AI agenata je differentiator na intervjuu — pokazuje da QA ne samo testira AI, vec i koristi AI za unapredjenje sopstvenog rada.
