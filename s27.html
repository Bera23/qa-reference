DEO II — AUTOMATSKO TESTIRANJE

📄 27. Templates✓ Procitano

⏱ ~3 min citanja

Koncepti iza svakog od ovih formata su objasnjeni u svojim sekcijama (test case u 5, bug report u 6, test plan u 7) — ovo su prazni sabloni za direktno kopiranje, bez teorije.

27.1 Bug report — prazan template

Title: [Komponenta] - [Kratak opis problema] - [Uslov pod kojim se javlja]

Environment: [Browser/verzija, OS, test okruzenje, verzija aplikacije]

Preconditions: [Sta mora biti tacno pre koraka - rola, postojeci podatak, stanje sistema]

Steps to Reproduce:
1. [Korak]
2. [Korak]
3. [Korak]

Actual Result: [Sta se stvarno desilo]

Expected Result: [Sta je trebalo da se desi]

Severity: [Blocker / Critical / Major / Minor / Trivial]
Priority: [High / Medium / Low]

Attachments: [Screenshot, video, log, HAR fajl]
Puna definicija Severity/Priority nivoa i primeri dobrog naslova su u Sekciji 6.

27.2 Test plan — prazan template

1. Test Plan Identifier: [Naziv/verzija]

2. Scope
   In scope: [Sta se testira]
   Out of scope: [Sta se NE testira i zasto]

3. Test Items: [Feature-i/moduli koji se testiraju]

4. Approach: [Nivoi testiranja, tehnike, manuelno vs. automatizovano]

5. Entry Criteria: [Sta mora biti spremno pre pocetka testiranja]
6. Exit Criteria: [Kada se testiranje smatra zavrsenim]

7. Environment: [Okruzenja, test podaci, potrebni pristupi]

8. Resursi i raspored: [Ko testira sta, procena vremena]

9. Rizici: [Rizik] - [Verovatnoca] - [Uticaj] - [Mitigacija]

10. Deliverables: [Test case-ovi, izvestaji, defect log]
Razlika izmedju test strategije (visok nivo, vazi za vise projekata) i test plana (konkretan, za jedan projekat/release) je u Sekciji 7.1.

27.3 Test case — prazan template

Title: [Modul]_[Sta se testira]_[Ocekivani ishod]

Preconditions: [Sta mora biti tacno pre izvrsavanja - rola, podaci, stanje]

Steps:
1. [Korak]
2. [Korak]
3. [Korak]

Expected Result: [Precizno i verifikabilno - ne "radi ispravno"]

Priority: [High / Medium / Low]
Type: [Smoke / Sanity / Regression / Functional]
Sta cini test case dobrim (atomican, nezavisan, ponovljiv) je u Sekciji 5.2.

27.4 Checklist za code review test koda

[ ] Naziv testa prati konvenciju (Method_State_Expected, Sekcija 19.4)
[ ] Test je atoman - proverava jednu stvar, ne vise nepovezanih asercija
[ ] Nema Thread.Sleep - koristi Explicit Wait (13.3)
[ ] Test podaci su izolovani - ne deli podatke sa drugim testovima (10.2)
[ ] Nema hardkodovanih vrednosti koje bi trebalo da budu u konfiguraciji (env URL, kredencijali)
[ ] Cleanup/teardown postoji ako test kreira podatke
[ ] Asercije proveravaju STVARNU posledicu akcije, ne samo da UI nije bacio gresku
[ ] Nema praznih catch blokova bez loga (19.7)
[ ] Test prolazi lokalno I u CI okruzenju
[ ] Ako je flaky-prone (npr. animacija, async ucitavanje) - ima odgovarajucu wait strategiju, ne retry kao prvi izbor

27.5 Checklist za release

[ ] Regression suite prosao na target okruzenju
[ ] Svi Blocker/Critical defekti zatvoreni ili svesno odlozeni uz potpis PO-a
[ ] Smoke test na produkcionoj (ili produkciji-najslicnijoj) konfiguraciji
[ ] Migracije podataka testirane na kopiji produkcionih podataka, ne samo na test setu
[ ] Rollback plan postoji i proveren
[ ] Release notes azurirani (sta je novo, sta je fix, poznati problemi)
[ ] Monitoring/alerting aktivan za novu funkcionalnost pre nego sto ode live
[ ] Tim koji radi support obavesten sta se menja
Environment checklist za pripremu SAMOG test okruzenja (ne release-a) je poseban i nalazi se u Sekciji 10.8.

⚡ Quick Reference

Severity nivoi

BlockerSistem se ne moze koristiti. Testiranje je blokirano. Nema workaround-a.Sistem ne radi, nema workaround-a
CriticalKriticna funkcionalnost je slomljena. Korisnik ne moze da dovrsi kljucni task.Kriticna funkcionalnost slomljena
MajorZnacajna funkcionalnost ostecena. Workaround postoji ali je neudoban.Znacajna funkcionalnost ostecena
MinorManja funkcionalnost ostecena. Prihvatljiv workaround postoji.Manja funkcionalnost, postoji workaround
TrivialEstetski problem — UI, tekst, formatiranje. Nema funkcionalnog uticaja.Estetski problem, bez funkcionalnog uticaja

Severity vs. Priority

SeverityTehnicki uticaj na sistem — koliko je funkcionalnost ostecena (Sekcija 6.3).Tehnicki uticaj
PriorityPoslovni uticaj i hitnost ispravke (Sekcija 6.3).Poslovna hitnost
High S · High PCrash na checkout-u u produkciji. Hitno, odmah.Crash na checkout-u u produkciji
High S · Low PCrash na admin stranici koju koristi 1 osoba mesecno. Vazno, ali ne hitno.Crash na retko koriscenoj stranici
Low S · High PLogo klijenta pogresno napisan dan pre prezentacije. Kosmeticko, ali hitno.Pogresan logo pred prezentaciju
Low S · Low PTypo u footer-u. Fiksirati kad bude prilike.Typo u footer-u

HTTP metode

GETCitanje resursa, bez side-effecta. Idempotentna i safe (Sekcija 15.1).Cita · idempotentna, safe
POSTKreiranje novog resursa. Ponovljen POST moze napraviti duplikat — zato je idempotentnost vazna za testiranje.Kreira · nije idempotentna
PUTPotpuna zamena resursa. Isti zahtev poslat dvaput daje isto stanje.Puna zamena · idempotentna
PATCHParcijalna izmena. Ne garantuje idempotentnost — zavisi od implementacije.Parcijalna izmena · nije idempotentna
DELETEBrisanje resursa. Drugi poziv ne menja stanje (odgovor moze biti drugaciji, npr. 404).Brise · idempotentna

HTTP status kodovi

200 OKUspesno obradjen zahtev. Vraca se za GET i za akcije koje ne kreiraju resurs.Uspesno
201 CreatedResurs je kreiran. Vraca se za uspesni POST. Obicno ukljucuje Location header.Resurs kreiran (POST)
204Uspesno obradjen zahtev, bez tela odgovora. Tipicno za DELETE.Uspesno, bez tela (DELETE)
400Nevalidan zahtev — los JSON, nedostaju obavezna polja. Cest ishod negativnih testova.Nevalidan zahtev
401Token nedostaje ili je neispravan. Klijent treba da se autentifikuje.Nedostaje token
403Autentifikacija je ok, ali korisnik nema prava na ovaj resurs.Token validan, nema dozvolu
404Resurs ne postoji na ovoj URL-i.Resurs ne postoji
409Konflikt sa trenutnim stanjem — npr. kreiranje korisnika sa emailom koji vec postoji.Konflikt (npr. duplikat)
422Format zahteva je ok, ali semanticki nije validan (narusena biznis pravila).Semanticki nevalidan zahtev
429Previse zahteva u kratkom vremenu — rate limiting.Rate limiting
500Greska na serveru. Uvek je defekt — developer mora da je ispravi.Greska na serveru — uvek defekt
502 / 503502: upstream servis ne odgovara. 503: servis trenutno nedostupan. Najcesce infrastruktura ili dostupnost servisa — proveriti okruzenje pre prijave defekta.Servis nedostupan — proveri okruzenje

Selenium: lokatori i wait-ovi

IDUvek koristiti kada je dostupan. Najbrzi i najstabilniji (Sekcija 13.2).Prvi izbor, najstabilniji
data-testidAtribut koji tim dodaje iskljucivo za testove. Idealan — dogovori se sa development timom.Idealan, dogovori sa dev timom
CSSFleksibilan, brz, citljiv. Preferovati nad XPath-om.Preferiraj nad XPath-om
XPathNajfleksibilniji, ali sporiji i krhkiji. Izbegavati indekse (//div[3]/span[2]) — krhko pri svakoj UI promeni.Poslednja opcija
Thread.SleepNije wait strategija. Uvodi fiksna kasnjenja i cini testove sporim i nestabilnim (Sekcija 13.3).Nije wait strategija
Explicit WaitCeka na konkretan uslov za konkretan element. Preporuceni pristup.Preporuceno
Implicit WaitGlobalno podesavanje na svaki FindElement. Moze maskirati probleme i usporiti testove.Izbegavati

Selenium exception-i

NoSuchElementElement nije pronadjen u DOM-u. Proveriti lokator, dodati Explicit Wait i proveriti da li je driver u pravom iframe/window kontekstu (Sekcija 13.9).Lokator, Wait, frame kontekst
StaleElementElement pronadjen ali DOM se promenio pre interakcije. Re-locate element.Re-locate element
NotInteractableElement postoji ali je skriven, disabled ili prekriven drugim elementom.Cekati na clickability
ClickInterceptedDrugi element (modal, overlay) prekriva ciljni element pri kliku.Sacekati da overlay nestane
TimeoutExplicit Wait nije pronasao ocekivani uslov u zadatom vremenskom okviru.Povecati timeout / proveriti lokator

Smoke / Sanity / Regression

SmokeBroad + Shallow. Pokrece se na svakom novom build-u. Go/No-Go odluka za dalji QA.Broad + Shallow · svaki build
SanityNarrow + Deep. Pokrece se nakon specificnog bugfix-a ili nove funkcionalnosti.Narrow + Deep · nakon fix-a
RegressionBroad + Deep. Pokrece se pre svakog release-a. Pokriva ceo scope.Broad + Deep · pre release-a
RetestingPonovo se izvrsava konkretan TC koji je prethodno failovao, nakon bugfix-a.Konkretan TC koji je failovao

Test tehnike — sta kad

EP + BVAEP: jedan reprezentativni element iz svake particije. BVA: granica, jedan ispod i jedan iznad. Godine 18-65: 17, 18, 19, 64, 65, 66 (Sekcija 4.1-4.2).Numericka polja, datumi, opsezi
Decision TableKombinacije uslova i ocekivanih akcija (Sekcija 4.3).Vise uslova, biznis pravila
State TransitionPonasanje zavisi od trenutnog stanja i prelaza (Sekcija 4.4).Workflow, statusi, multi-step
PairwiseVecina defekata nastaje pri interakciji dva parametra, ne svih N. 3 x 3 x 3 = 27 kombinacija svodi se na oko 9 (Sekcija 4.5).Vise parametara, compatibility
ExploratoryKad nema dovoljno specifikacije — istrazivanje uz beleske (Sekcija 4.8).Novi feature, slaba specifikacija
Error GuessingIskustvo o tome sta tipicno pukne. Kao dopuna, ne zamena (Sekcija 4.6).Dopuna, iskusan QA
