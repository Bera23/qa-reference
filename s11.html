DEO II — AUTOMATSKO TESTIRANJE

🤖 11. Uvod u automatizaciju✓ Procitano

⏱ ~2 min citanja

11.1 Kada automatizovati, kada ne

Dobri kandidati:

  • Regression testovi koji se izvrsavaju cesto — svaki sprint ili svaki build.
  • Smoke i sanity testovi koji blokiraju dalji rad ako failuju.
  • Testovi sa velikim brojem iteracija podataka (data-driven scenariji).
  • Repetitivni, vremenski intenzivni manuelni testovi.
  • Cross-browser i cross-platform testovi.

Losi kandidati:

  • Jednokratni testovi ili scenariji koji se retko izvrsavaju.
  • Exploratory testiranje — zahteva kognitivni rad i adaptaciju.
  • UI testovi na veoma nestabilnom UI-u sa cestim layout promenama.
  • Feature koji ce se menjati u sledecoj iteraciji.

11.2 ROI automatizacije

Breakeven = Vreme pisanja / Manuelno vreme po run-u

  Primer: Manuelno 2h, Pisanje 8h -> Breakeven = 4 run-a
  Pokretanje jednom mesecno -> isplati se (breakeven za 4 meseca).
  Pokretanje jednom godisnje -> ne isplati se.
Odrzavanje je skriveni trosak koji se najcesce podcenjuje — nestabilan UI, promene lokatorima, refaktoring aplikacije. Senior QA mora da ga ukljuci u procenu od pocetka.

11.3 Test automation piramida i trofej

Piramida (Mike Cohn):
            ^
           /E2E/           <- Mali broj, sporiji
          /Integra/         <- Srednji nivo, API testovi
         /  Unit   /        <- Najveci broj, brzi

Trofej (Kent C. Dodds):
            ^
           /E2E/            <- Malo (kriticni happy path)
          /Integra/          <- Najveci deo
         /  Unit  /          <- Manje nego u piramidi
        / Static  /          <- TypeScript, linting
Anti-pattern — Ice Cream Cone: mnogo E2E testova, malo unit testova. Testovi su spori, krhki i skupi za odrzavanje.

11.4 Flaky testovi — uzroci i strategije

Najcesti uzroci:

  • Hardkodovana cekanja (Thread.Sleep) umesto Explicit Wait.
  • Zavisnost od redosleda izvrsavanja testova.
  • Race condition — test je brzi od UI-ja ili API-ja.
  • Dinamicki lokatori koji se menjaju izmedju run-ova.

Strategije resavanja:

  • Izolovati flaky testove odmah — oznaciti tagom, ne ignorisati.
  • Analizirati failure pattern — pada li samo u CI, samo u odredjeno vreme?
  • Retry logika samo za infrastrukturne greske, ne za legitimne failove.
  • Svaki flaky test tretirati kao bug — uci u backlog.

11.5 Mock, Stub i Spy — razlika

StubLazna implementacija koja vraca predefinisani odgovor. Ne verifikuje kako je pozvana — samo zamenjuje zavisnost.
MockVerifikuje i kako je pozvana: koliko puta, sa kojim argumentima. Ako ocekivanje nije ispunjeno, test pada.
SpyOmotac oko realne implementacije. Poziva pravu metodu, ali belezi pozive za naknadnu verifikaciju.
Za osnovne definicije Error/Defect/Failure videti Sekciju 1. Piramida i trofej su strategije rasporeda testova po nivoima iz Sekcije 3.
// Stub — vraca vrednost, ne proverava poziv
var stub = new Mock();
stub.Setup(p => p.Charge(It.IsAny())).Returns(new Result { Success = true });

// Mock — verifikuje da je metoda pozvana tacno jednom
var mock = new Mock();
mock.Setup(p => p.Charge(99.99m)).Returns(new Result { Success = true });
// ... izvrsiti kod ...
mock.Verify(p => p.Charge(99.99m), Times.Once);
