🏗️ 13. Page Object Model✓ Procitano

⏱ ~1 min citanja

13.1 Sta je POM i zasto postoji

Page Object Model je design pattern koji enkapsulira UI lokatore i interakcije za odredjenu stranicu u posebnu klasu. Test kod komunicira sa stranicom iskljucivo kroz metode te klase — nikad direktno sa lokatorima.

  • Separacija brige — lokatori i UI logika odvojeni od test logike.
  • Odrzivost — promena lokacije elementa zahteva izmenu samo u Page klasi.
  • Citljivost — testovi opisuju ponasanje, ne implementacione detalje.
  • Ponovna upotreba — iste metode se koriste u vise testova.

13.2 Struktura POM projekta (C#)

TestProject/
  Pages/
    BasePage.cs           // Zajednička logika svih stranica
    LoginPage.cs          // Lokatori + metode za Login stranicu
    DashboardPage.cs
  Tests/
    BaseTest.cs           // Setup/TearDown, driver inicijalizacija
    LoginTests.cs
  Helpers/
    DriverFactory.cs      // Kreiranje WebDriver instance
    TestDataBuilder.cs
  Config/
    appsettings.Test.json
    appsettings.CI.json

13.3 Implementacija Page klase

public class LoginPage : BasePage
{
 private By EmailField    => By.CssSelector(input[name=email]);
 private By PasswordField => By.CssSelector(input[name=password]);
 private By LoginButton   => By.CssSelector(button[type=submit]);
 private By ErrorMessage  => By.CssSelector(.alert-error);

    public LoginPage(IWebDriver driver) : base(driver) { }

    public void EnterEmail(string email)
        => WaitForVisible(EmailField).SendKeys(email);

    // High-level composite akcija
    public DashboardPage LoginAs(string email, string password)
    {
        EnterEmail(email); EnterPassword(password);
        return ClickLogin();  // vraca sledecu stranicu
    }
}

13.4 Page Factory

Alternativni nacin definisanja lokatorima — koristi [FindsBy] atribute i PageFactory.InitElements(). Cest u starijim C# i Java projektima.

Page Factory se NE preporucuje u novim projektima. Interno koristi lazy initialization sa implicit wait logikom — moze maskirati probleme i ponasati se neocekivano sa StaleElementReferenceException.

13.5 Kada POM postaje problem

  • Over-engineering na jednostavnim projektima — 10 TC-ova ne zahtevaju punu POM arhitekturu.
  • Page klase postaju prevelike — ako LoginPage ima 50 metoda, pokriva previse odgovornosti.
  • Teske za odrzavanje pri cestim UI promenama.
  • Ugnjezdeni Page objekti — navigacija postaje komplikovana.
Alternativa za kompleksne scenarije: Screenplay pattern — modelira interakcije kao User + Abilities + Tasks + Questions.
